# Resources

Open these when the distilled reference files aren't enough. Free unless marked paid.

| Resource | Use it when |
|----------|-------------|
| [Laws of UX](https://lawsofux.com) | You need the one-paragraph definition and origin of a law (Hick, Fitts, Jakob, goal-gradient, peak-end) to teach it accurately |
| [GOV.UK Design System](https://design-system.service.gov.uk) ([source](https://github.com/alphagov/govuk-design-system)) | Designing any form, question flow, error message, or "check your answers" step; patterns are tested with millions of real users |
| [Nielsen Norman Group](https://www.nngroup.com/articles/) | You need research-backed guidance on a specific topic (empty states, mobile navigation, error messages); search their articles first |
| [Nielsen's 10 heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) | Explaining a heuristic in the audit by its original wording |
| [Growth.Design case studies](https://growth.design/case-studies) | Teaching a psychology concept through a real app's onboarding or paywall, comic-style; good for showing the user why a pattern works |
| [Material Design 3](https://m3.material.io) | Android conventions, component behavior, and accessibility specs; the default for Android and a solid neutral reference for web |
| [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines) | iOS conventions; for audits, use the `hig` skill in this plugin, which distills it |
| [WCAG 2.2 quick reference](https://www.w3.org/WAI/WCAG22/quickref/) | Checking an exact accessibility requirement (contrast, target size, focus) |
| [Inclusive Components](https://inclusive-components.design) | Building an accessible toggle, menu, tab set, card, or notification on the web, with the reasoning behind each choice |
| [Page Flows](https://pageflows.com) (paid) | Video recordings of full flows when Mobbin lacks the app |
| [Mobbin](https://mobbin.com) (paid) | Teardown mode: real screens and flows from shipped apps, searchable by pattern; the MCP integration searches it directly |
| [Refactoring UI](https://www.refactoringui.com) (paid) | Fixing visual hierarchy, spacing, and "everything looks the same weight" problems with practical before/after tactics |

## Concepts worth knowing by name

| Plain words | Term | Named after / coined by |
|-------------|------|--------|
| The job a person hires a product to do | Jobs to Be Done | Clayton Christensen, Bob Moesta |
| The moment a new user first gets real value | Activation | Product analytics practice |
| The one number that captures value delivered | North Star metric | Amplitude, Sean Ellis |
| Fewer choices, faster decisions | Hick's law | William Hick and Ray Hyman |
| Big, close targets are faster to hit | Fitts's law | Paul Fitts |
| People expect your app to work like others | Jakob's law | Jakob Nielsen |
| People speed up near the finish | Goal-gradient effect | Clark Hull |
| The end shapes the memory | Peak-end rule | Daniel Kahneman |
| The different thing gets noticed | Von Restorff effect | Hedwig von Restorff |
| Unfinished tasks stick in memory | Zeigarnik effect | Bluma Zeigarnik |
| Fast responses keep people in flow | Doherty threshold | Walter Doherty and Ahrvind Thadani (IBM) |
| Some complexity can only be moved, not removed | Tesler's law | Larry Tesler |
| Working memory holds only a few items | Miller's law | George Miller |
